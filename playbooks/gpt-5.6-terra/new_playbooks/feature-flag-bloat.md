# Feature-flag bloat

> **Risk tier:** high · **Applies to:** EDS, CS, Headless

## What this addresses

Optional capabilities can remain in shipped JavaScript when a feature flag is evaluated from runtime configuration rather than replaced with a literal during the production build. Making a confirmed-disabled capability statically removable can allow the minifier to remove unused code and reduce bundle size.

## When to apply / when to skip
**Apply when:**
- Bundle analysis identifies a disabled optional capability, such as replay, analytics integration, WebGL, or an experiment runtime, in the JavaScript shipped to an affected route.
- The capability is disabled consistently for the deployment and its flag can be replaced at build time with a literal boolean.
- The build pipeline performs define replacement and production minification or tree-shaking.
- Functional testing can cover every route and integration affected by removing the capability.
- The generated production artifact can be inspected to confirm that the optional module is no longer emitted or delivered.

**Do not apply when:**
- The flag varies per visitor, tenant, authorable page, consent state, experiment assignment, or request. It is a runtime decision and cannot safely be removed from the bundle.
- The bundle is generated by an opaque third-party clientlib, CDN artifact, or vendor package that the project cannot rebuild.
- The production artifact still contains the feature flag or optional module after a test build.
- The capability’s dependencies, fallback behavior, or operational ownership are not known.

This is recommendation-only. Incorrect build-time flags can remove a required runtime path, so do not emit an automatic code change without bundle inspection and route-level functional validation.

## Recommended approaches

### Use a literal build-time capability flag around an EDS block import

Keep the optional capability behind a global constant that the production build replaces with `true` or `false` before minification. When the capability is disabled, the minifier can remove the unreachable branch and the block-relative dynamic import.

**Good:**

**EDS:**

```javascript
// blocks/store-locator/store-locator.js
// BUILD_ENABLE_STORE_LOCATOR is replaced with false by the production build.

export default function decorate(block) {
  if (!BUILD_ENABLE_STORE_LOCATOR) {
    block.remove();
    return;
  }

  const observer = new IntersectionObserver((entries) => {
    if (!entries[0].isIntersecting) return;

    import('./locator.js')
      .then(({ decorateLocator }) => decorateLocator(block))
      .finally(() => observer.disconnect());
  });

  observer.observe(block);
}
```

**CS:**


### Remove disabled capabilities from a headless client bundle at build time

For headless delivery, retain runtime configuration only for behavior that must vary at runtime. Use a build-time constant for capabilities that are disabled for the entire deployed client application.

**Good:**

**EDS:**

```javascript
// blocks/site-runtime/site-runtime.js
// BUILD_ENABLE_SESSION_REPLAY is replaced with false during the production build.

export default function decorate(block) {
  if (BUILD_ENABLE_SESSION_REPLAY) {
    import('./session-replay.js').then(({ initializeReplay }) => {
      initializeReplay();
    });
  }

  fetch('/content/site/us/en.model.json')
    .then((response) => response.json())
    .then((model) => {
      block.dataset.modelLoaded = 'true';
      block.textContent = model.title || '';
    });
}
```

## Anti-patterns

### Runtime configuration object prevents dead-code elimination

**Bad:**

**EDS:**

```javascript
// blocks/session-replay/session-replay.js
// Bad: the value is only available in the browser at runtime.

export default function decorate(block) {
  const featureFlags = window.siteConfig?.features;

  if (featureFlags?.sessionReplay?.isEnabled) {
    import('./session-replay.js').then(({ initializeReplay }) => {
      initializeReplay(block);
    });
  }
}
```

```javascript
    initializeReplay();
  });

```

**Why this is bad:** A flag read from `window` is only known in the browser, so a production build cannot use that value as a compile-time constant to remove the optional path.

### Passing one opaque runtime flag object to every optional module

**Bad:**

**EDS:**

```javascript
// blocks/site-capabilities/site-capabilities.js
// Bad: every optional module is requested before runtime configuration decides enablement.

export default function decorate(block) {
  Promise.all([
    import('./analytics.js'),
    import('./maps.js'),
    import('./session-replay.js'),
  ]).then(([analytics, maps, replay]) => {
    const capabilities = window.siteConfig?.capabilities || {};

    analytics.initializeAnalytics(capabilities, block);
    maps.initializeMaps(capabilities, block);
    replay.initializeReplay(capabilities, block);

}
```

```javascript
const capabilities = getPageConfiguration().capabilities;

initializeMaps(capabilities);
```

**Why this is bad:** These imports or clientlib inclusions include the optional modules before their enablement can be decided from runtime configuration.

## Flavor-specific notes

### EDS

Use deployment-level build constants only for features that are consistently disabled across the EDS site. Keep optional code in separately imported modules and inspect the generated artifact after disabling the feature.

Verify that the generated bundle no longer contains the disabled build flag or optional code path before treating the reduction as complete.

### CS and AMS

The cited evidence supports build-time constants and production tree-shaking, not any specific clientlib packaging behavior. Confirm how the relevant clientlib JavaScript is built, whether build-time replacement is available, and whether the published page includes only the required client assets.

Do not use an author-editable component property as a build-time flag unless every possible authored value is represented by a separately built and tested artifact.

### Headless

Restrict static elimination to capabilities that are disabled for the complete deployed client application. For behavior that must vary by tenant, visitor, experiment, consent state, or request, preserve the runtime path rather than treating the value as a build-time constant.
